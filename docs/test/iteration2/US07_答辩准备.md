# US07 答辩准备文档

日期：2026-04-12

## 1. 我负责的功能

我负责的是 **US07：查看申请状态时间线**。

该功能的目标是：

1. TA 可以查看自己每条申请的当前状态。
2. TA 可以按时间顺序查看申请状态变化时间线。
3. TA 可以看到每条申请的最近更新时间。

一句话概括：

> 我把原本只有申请记录的功能扩展成了一个完整的状态跟踪闭环：提交申请时记录起点，MO 更新状态时追加时间线事件，TA 端可以查看当前状态、完整时间线和最近更新时间。

## 2. 功能实现说明

本次实现按照 **MVC + DAO / Service + JSON 模拟数据库** 的项目规范开发，并和现有 `style.css`、`home.jsp` 风格保持一致。

### 2.1 状态设计

沿用并扩展了存储层状态码：

- `SUBMITTED`
- `IN_REVIEW`
- `SHORTLISTED`
- `ACCEPTED`
- `REJECTED`

在 TA 页面上的展示文案统一转换为：

- Submitted
- In Review
- Shortlisted
- Accepted
- Rejected

同时修正了 `ApplicationService.updateApplicationStatus` 的状态支持范围。  
之前拒绝 `SUBMITTED`，与 MO 端下拉框不一致；现在已允许上述全部状态。

另外，MO 审核页面的下拉框新增了 `IN_REVIEW`，并且 `ApplicantReviewService` 中的排序逻辑也加入了 `in_review` 档位。

### 2.2 时间线设计

新增了独立的时间线数据文件和结构：

- `data/timelines.json`
- `TimelineEvent`
- `TimelineDao`

写入规则如下：

1. TA 提交申请时，自动写入一条 `SUBMITTED` 事件。
2. MO 修改申请状态且与旧状态不同的时候，自动追加一条对应状态事件。
3. 状态事件可以带备注摘要，便于在时间线上展示补充说明。

为了兼容旧数据，我还处理了历史申请没有时间线的问题：

1. 如果旧申请完全没有时间线记录，就根据 `submittedAt`、当前状态和 `updatedAt` 自动合成最少时间线。
2. 如果已经存在时间线，但首条不是 `SUBMITTED`，系统会自动补上一条“已提交”节点。

这样可以避免 TA 打开页面时只看到后续阶段，看不到申请的起点。

### 2.3 最近更新时间

每条申请卡片都会展示 `Application.updatedAt` 的格式化时间。

因为申请状态每次变更时都会刷新 `updatedAt`，所以这个字段就可以反映当前申请最近一次被处理的时间。

## 7. 关键设计点解释

### 7.1 为什么要单独设计 TimelineEvent 和 TimelineDao

因为时间线本质上不是申请对象上的一个普通字段，而是一组按时间累积的事件。

如果直接把所有时间线逻辑塞进 `Application` 或 `ApplicationDao`，会导致职责混乱。  
所以我把时间线单独拆成：

1. `TimelineEvent`：表示单个状态事件
2. `TimelineDao`：专门负责时间线 JSON 的读写

这样做能让申请主数据和时间线数据的职责更清晰，也更方便扩展。

### 7.2 为什么需要 ApplicationTimelineRecorder

因为状态变化的时间线写入逻辑会在多个地方触发：

1. TA 提交申请时
2. MO 修改状态时

如果把这部分逻辑直接分散写在各个 Servlet 或 Service 里，会造成重复代码。  
所以我把“追加时间线事件”的逻辑集中到 `ApplicationTimelineRecorder` 中，统一管理记录行为。

### 7.3 为什么要对旧数据做兼容处理

因为在 US07 开发前，系统里已经存在旧申请数据，但这些旧数据没有完整时间线记录。

如果不做兼容，TA 页面会出现两个问题：

1. 打开页面看不到任何时间线
2. 或者只能看到后续状态，看不到最开始的提交节点

所以我做了两层兜底：

1. 无时间线记录时，用 `submittedAt + 当前状态 + updatedAt` 合成最少时间线
2. 如果首条不是 `SUBMITTED`，自动补上“已提交”节点

这样旧数据也能稳定展示。

### 7.4 为什么要显示最近更新时间

因为“当前状态”只能说明结果，“最近更新时间”可以帮助 TA 理解申请最近一次被处理的时间点。

这对用户体验很重要。  
例如两个申请都处于 `In Review`，但最近更新时间不同，TA 能判断哪一个更近期被处理过。

### 7.5 为什么要加入 HtmlEscape

时间线备注、职位标题等内容最终会显示到页面上。  
为了避免用户输入的内容直接进入 HTML 渲染，增加了 `HtmlEscape` 做输出转义。

这体现了我在页面展示层同时考虑了安全性，而不只是完成功能。

## 8. 老师可能会问的问题和回答

### 问题 1：为什么时间线要单独建一个 JSON 文件，而不是直接放在 applications.json 里？

回答：

因为时间线是一组动态累积事件，和申请本身的主属性不同。  
单独拆出来后，DAO 和 Service 的职责更清晰，也更方便后续扩展和维护。

### 问题 2：为什么要补旧数据的时间线？

回答：

因为系统在 US07 开发前已经有旧申请数据，如果直接上线时间线页面，旧数据就无法正确展示。  
做兼容处理可以保证历史申请也能看到合理的时间线，不会出现空白或缺少起点的问题。

### 问题 3：为什么要新增 IN_REVIEW？

回答：

因为审核过程不应该只有提交和最终结果，中间需要一个明确的“审核中”阶段。  
另外 MO 页面原有流程和存储层状态不完全一致，所以我把状态定义统一起来，并同步更新排序逻辑。

### 问题 4：最近更新时间和时间线有什么区别？

回答：

时间线反映的是完整过程，最近更新时间反映的是最后一次处理时间。  
两个信息的粒度不同，放在一起展示，TA 才能更快理解申请状态。

### 问题 5：你这部分体现了什么工程设计思想？

回答：

主要体现了分层设计、兼容性处理和可维护性。  
我没有把所有逻辑写进一个 Servlet，而是拆分成 Model、DAO、Service、Servlet 和 JSP，并对旧数据和页面安全做了额外处理。

> 我这部分实现的是 TA 侧的申请状态时间线功能，不只是显示当前状态，而是让用户看到每条申请从提交到当前阶段的完整过程，并补充最近更新时间。整个实现按 MVC + DAO/Service 分层完成，同时兼容了旧数据并补齐了时间线记录。
